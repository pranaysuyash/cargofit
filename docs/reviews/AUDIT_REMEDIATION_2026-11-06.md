# Cargo Fit audit remediation, 2026-11-06

## Decisions and evidence

- Suite URL imports previously filled omitted measurements, count, weight and payload with illustrative numbers as if declared. `suiteImport.ts` preserves missing numeric fields as `null`, preserves explicit zero for normal validation, and converts pounds or feet only when supplied. An aggregate weight is divided only by a supplied positive count. Fixed orientation and no-stack are conservative editable modeling defaults, explicitly disclosed in the UI; they are not evidence of physical handling requirements.
- A failed scenario-store read previously returned `[]`, allowing save or delete to replace unreadable data. The storage boundary now rejects unreadable, invalid JSON and structurally unrecognized data before writing. The save screen reports failure and offers a byte-for-byte text download when browser access permits, plus retry. It does not repair or remove the original. This validation checks the outer structures needed by the versions interface, not a complete schema migration or integrity verification. A browser denial can also prevent recovery download.
- Loading confirmation now distinguishes manual attestation, an entered code match and a camera scan match, including the matching method. These records are session-only and reset when the plan or manifest changes. They are not durable, identity-bound proof of physical loading. Legacy standalone code matching can be partial; connected declared barcodes still require exact matching.
- Assumed axle, restraint, dunnage and hazard calculations were described as statutory conclusions. Primary plan and report labels now identify assumptions and withhold estimates for unknown placed weights; hazard label guesses do not establish classification. The CoG overlay is an illustrative interior-length reference, not a universal optimum. Tandem values in the BOL are identified as modeled. This is an incremental truthfulness change, not a compliance or engineering validation of the underlying models.
- BOL readiness and printed totals previously trusted summary metrics even when a placed unit did not resolve to manifest weight. They now check and total placed manifest units directly and block final issuance for unknown or unmatched weights. The emergency phone inspected in the original fixture was explicitly supplied; the generator renders it only if provided. No default phone was found in that path.

## Verification and remaining work

Before the storage change, six of seven recovery cases failed, including a write after a read failure. Before the BOL change, an inconsistent plan with no resolvable manifest units was accepted for final issuance. Focused cases now exercise both boundaries, import nulls and conversions, matching methods, and report labels. Full automated results and runtime status belong in the current audit task register.

The hazard matrix still receives inferred classes and assumed weights; its detail output and other downstream consumers need a full typed declaration/provenance redesign and authoritative domain review before it can support an operational determination. Tandem state still contains a legacy `legal` boolean derived from modeled values; consumers beyond the inspected BOL path require tracing and migration. Other tool-specific detail views may contain unqualified recommendations or assumed numeric data and need a full audit. Real mobile/browser use, actual storage-denial recovery, screen reader behavior, and end-to-end connected scan workflows have not been verified by these unit tests. No test proves real-world load safety or regulatory compliance.

## Follow-up: restraint, tandem, hazard and CLI boundaries

The restraint model now only estimates placed, matched units with known positive weights; it exposes incomplete status and unknown/missing IDs. It retains the selected hardware and no longer infers a blanket chain mandate from cargo weight. Its results remain illustrative and are withheld from the UI/report when incomplete. Tandem recommendation text and the apply notification identify assumed benchmarks, not actual legal status. The legacy tandem `legal` field remains a model boolean for compatibility and requires a versioned migration before any external consumer may interpret it as authority.

Hazard display now preserves unknown weights and converts declared kilograms, pounds and tonnes correctly. A class is extracted only from explicit supported `Class` text; a UN number or vague description does not supply one. Unknown-class items are identified and excluded from pair comparison, and the legacy boolean is false for incomplete class data. Its report explicitly says `illustrative`; label text remains unverified, and absent gas zone, packing group, subsidiary hazards and package/mixture conditions cannot establish legality. The fixed 10-foot recommendation was removed: the [current eCFR § 177.848](https://www.ecfr.gov/current/title-49/subtitle-B/chapter-I/subchapter-C/part-177/subpart-C/section-177.848) describes separation to prevent commingling and contains additional conditional rules. The simplified matrix is not a substitute for a complete typed hazard declaration and qualified review. The legacy `compliant` boolean is retained only for compatibility and means no modeled prohibited pair with complete class text, not actual compliance.

The standalone CLI declared trailer dimensions in meters despite millimeter values, producing a 16,150,000 mm trailer. It now uses 16,150 mm and reports only illustrative axle/restraint estimates; absent placed weight or centroid makes those estimates unavailable. A manifest-to-CLI test reproduced the original dimensional error; tests also cover unknown weight. Focused hazard/CLI, restraint and tandem tests and the full P01 suite were run; see the current task register for exact receipts. Printed/browser rendering and actual cargo conditions remain unverified.

## Scoped modeled estimates and legacy recovery

Tandem and density modals formerly wrote unscoped global browser keys, and the export path consumed those values even after a scenario, equipment or arrangement change. New writes use one `cargo_fit_modeled_artifacts_v1` store containing typed estimates tied to the exact serialized scenario, equipment, arrangement index, placements and modeled multi-stop stage. Plan and BOL export use the same selector and withhold estimates from another scope. The full serialized input is compared rather than relying on the short non-cryptographic scenario hash. A malformed or unrecognized new store is not overwritten, and a failed write or read-back produces an in-session-only warning.

The old `cargo_fit_active_tandem_config` and `cargo_fit_active_nmfc_summary` keys are retained without automatic migration or deletion because they do not contain reliable source identity. The Versions screen offers a user-triggered raw download for review. To make an old estimate usable, review and reapply it against the current arrangement; only that new explicit action writes the scoped store. A future migration or cleanup must preserve those raw legacy values unless the owner explicitly authorizes otherwise. Browser multi-tab synchronization and corruption recovery for the new consolidated store are still open; no atomic cross-tab merge is claimed.

The density advisor no longer substitutes 18,500 lb or 950 cubic feet for missing values, withholds its result until positive inputs exist, and records the editable weight, volume and DIM factor assumptions with its estimate. It remains a density illustration, not a certified NMFC class or verified carrier bill. The BOL labels its density result as illustrative; the separate operator-entered line classification is unchanged.

The dunnage geometry retains unknown cargo weight as `null`; its current heuristic uses geometry and does not use weight. Its six-inch threshold and suggested equipment are model assumptions, not a universal statutory maximum. [49 CFR § 393.106](https://www.ecfr.gov/current/title-49/subtitle-B/chapter-III/subchapter-B/part-393/subpart-I/section-393.106) describes securement requirements but does not establish the model's blanket six-inch rule. Legacy field names remain for compatibility and must not be interpreted as legal compliance. Focused tests reproduced the stale/unscoped, unknown-input and misleading-notice boundaries; current full-suite and typecheck results are recorded in the shared task register. Browser download, cross-tab behavior and physical securement remain unverified.

## Document review and status export

BOL approvals and session signatures are tied to the exact plan, selected modeled artifacts, document fields and line declarations. Generation-only timestamps are excluded. Changing the document withholds stale evidence, while entered details remain available for another review. The tracked CLI is rebuilt from its source with one entry point; subprocess tests cover correct equipment dimensions, a single invocation and failure exit status.

The EDI 214 generator requires actual declared partner identifiers, shipment and BOL identifiers, interchange control, event time, location, status, reason and usage. It omits optional seal, equipment and quantities when absent, rejects invalid field content, and places event date and time in their correct AT7 positions. The [SAP X12 214 implementation guideline](https://help.sap.com/doc/sap-business-network-x12-qm214-4010-inbound/cloud/en-US/SAP%20Business%20Network%20X12%20QM214%204010%20Inbound.pdf) was consulted; the generated message still requires validation against the actual trading partner's agreement. Nothing is transmitted by this export.

A local browser check using the supplied sample observed missing accessible names on repeated line inputs and internal names on the BOL form. Human-readable labels and item-specific accessible names are now provided. The same check observed approval clear when a carrier field changed and a missing-SCAC error on an incomplete EDI export. Typecheck and 17 focused scope/BOL/EDI tests passed. This is a local browser observation, not evidence of real signatures, partner acceptance, a complete screen-reader audit or a real cargo operation.
